> 這篇擴寫於 2026 年 11 月，底稿是我 2023 年寫在 HackMD 上的競程演算法教學筆記（第 1 章），當時只寫給社團學弟妹看。這次補上幾年打下來的實際體感，順手把當年寫得比較簡陋的定義整理乾淨。

## 複雜度在分析什麼

複雜度（Complexity）用來分析一個解法所需的計算量與記憶體空間，藉此比較解法的優劣、幫助取捨。同一份程式碼在不同機器上跑出來的秒數會差很多，但機器每秒能做的基本計算量是固定的，執行時間和計算量成正比，所以我們談的一直是計算量，時間只是它的推論。空間複雜度則是計算過程中，同一時刻最大的儲存需求。

競程的題目有時間與記憶體限制，程式必須在時限內跑完，所以複雜度分析的第一個用途是判斷解法可不可行。如果省略不提，單說「複雜度」通常指時間複雜度。空間通常不是瓶頸，能用空間換計算量的話幾乎都划算，除非開出來的陣列直接爆掉記憶體上限。

## 為什麼省略常數、只看最壞情況

資料量小的時候，百分之一秒和萬分之一秒的差距根本感覺不出來；但資料放大一百倍、一千倍之後，一天和一百天的差距就致命了。所以我們在意的是計算量隨資料量成長的速度，也就是資料量大時的表現，小資料反而快慢無所謂。

影響實際耗時的細節太多：加減乘除背後的指令數不同、實作手法不同、語言和編譯器也不同，這些差異都反映成常數倍率，乾脆全部省略。另外我們通常只在意極端情況——就像防淹水只看暴雨，不管毛毛雨——所以慣例上盯著最壞情況的計算量看。

## Big O 到底是什麼

我當年筆記的定義寫得蠻隨便，這裡補嚴謹一點。Big O 描述函數成長的上界：

$$O(g(n)) = \{f(n) : \exists\, c > 0,\ n_0,\ 0 \le f(n) \le c \cdot g(n)\ \text{for all } n \ge n_0\}$$

白話講，n 夠大之後 f(n) 不會超過 g(n) 的某個常數倍。對應地，$$\Omega(g(n))$$ 是下界，$$\Theta(g(n))$$ 是上下同時夾住的緊界。證明就留給演算法老師了吧。

實務上有個公開的祕密：競程圈說「這題是 $$O(n \log n)$$」時，幾乎都在口語混用 Big O 和 Theta。嚴格來說，快速排序最壞情況是 $$O(n^2)$$，說「快速排序是 $$O(n \log n)$$」講的其實是 Theta；把下界用 O 表達在數學上是錯的（任何函數都是 $$O(n)$$），但大家講得理直氣壯，聽懂就好，要寫證明時才需要分清楚。

常見的階從小到大排：$$O(1)$$、$$O(\log n)$$、$$O(n)$$、$$O(n \log n)$$、$$O(n^2)$$、$$O(2^n)$$，各自大致對應常數操作、二分搜、掃一遍、排序、雙重迴圈、枚舉子集合，記住這層對應比背定義有用。

## 從 n 範圍逆推解法

競程最實用的一招：先看題目的資料範圍，再反推可行的複雜度。圈內流傳的經驗法則是 judge 一秒大約能跑 $$10^8$$ 到 $$10^9$$ 次基本運算，這個說法在 Codeforces 和 LeetCode 的討論區被反覆引用，嚴格來說是 heuristic 而非定數，C++ 常數小可以衝上緣，Python 就得保守些。我的換算習慣：估算出的運算次數在 $$10^6$$ 以內很安全，$$10^8$$ 上下要看常數拚一下，再上去基本不用試。

具體例子：$$n = 2000$$ 時，$$O(n^2)$$ 代入是 $$4 \times 10^6$$，穩；$$O(n^3)$$ 是 $$8 \times 10^9$$，不用想了。反過來，看到題目寫 n ≤ 2000，就可以推測出題者預期的是 $$O(n^2)$$ 到 $$O(n^2 \log n)$$ 級別的做法——如果只想到暴力解，正解多半藏在「多一個 log」或「少一層迴圈」裡。同樣的直覺：n ≤ 20 通常暗示位元枚舉或搜尋剪枝，n ≤ $$10^5$$ 幾乎必然要求 $$O(n \log n)$$ 以內。把「範圍 → 複雜度 → 手法」這條鏈練熟，讀完題目就知道該往哪個方向想。

## 均攤分析

最後一個容易誤判的情境：不能光看單一操作的最壞情況。以動態陣列（Python 的 list、C++ 的 vector）為例，空間滿了要擴容時，得把整個陣列搬到新的位置，這一次操作就是 $$O(n)$$；但接下來的插入都能在常數時間完成。把 n 次插入的總成本 $$O(n)$$ 平均回去，每次操作均攤 $$O(1)$$。也就是說「某一次操作最壞 $$O(n)$$」和「n 次操作總共 $$O(n)$$」可以同時成立，分析時要看的是整個操作序列的總量，逐項取最壞再相加會把複雜度算得太悲觀。
