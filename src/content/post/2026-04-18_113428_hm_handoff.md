## 1. 系統架構概覽

Talkuma 是一個 Web App（PC-first），包含以下四個主要技術模組：

| 模組  | 職責  | 複雜度 |
|-----|-----|-----|
| 核心平台 | 帳號、公會、排程、動態牆、歷史記錄 | 中（標準 CRUD） |
| 即時通訊 | WebRTC 語音通話 + 螢幕共享 + 錄影 | 高   |
| LLM 回饋系統 | 初版分析（前期人工替代）+ AI Chatbot 互動 | 高   |
| 通知系統 | 站內通知 + Web Push + Email | 中   |

## 2. 認證系統

僅支援第三方 OAuth，不做 Email + 密碼。

| OAuth Provider | 說明  |
|----------------|-----|
| Google         | 主要登入方式 |
| GitHub         | 備選  |
| Discord        | 備選  |

註冊流程：OAuth 完成 → 若為新使用者 → 補填暱稱（必填，1-20 字元）+ 頭像（選填，預設用 OAuth 頭像）→ 建立帳號。

從邀請連結進入的註冊需額外處理：註冊完成後自動加入對應公會。

## 3. 資料模型（核心 Entity）

以下為概念模型，具體欄位與型別由後端自行設計。

### 3.1 User

| 欄位  | 說明  |
|-----|-----|
| id  | 主鍵  |
| nickname | 暱稱，1-20 字元 |
| avatar_url | 頭像 URL |
| email | 來自 OAuth provider，不可修改 |
| oauth_provider | google / github / discord |
| oauth_id | Provider 端的 user ID |
| notification_prefs | Email 通知開關、Web Push 開關 |
| created_at | 註冊時間 |

### 3.2 Guild（公會）

| 欄位  | 說明  |
|-----|-----|
| id  | 主鍵  |

| description | 最多 200 字元 |
| is_public | 公開 / 私人（影響是否出現在公會板） |
| leader_id | 公會長（FK → User） |
| created_at | 建立時間 |

業務規則：每人最多建立 1 個公會、最多同時加入 3 個公會。

### 3.3 GuildMember

| 欄位  | 說明  |
|-----|-----|
| guild_id | FK → Guild |
| user_id | FK → User |
| role | leader / member |

### 3.4 InviteLink（邀請連結）

| 欄位  | 說明  |
|-----|-----|
| id  | 主鍵  |
| guild_id | FK → Guild |
| token | 唯一 token |
| expires_at | 建立後 7 天到期 |
| created_by | FK → User（公會長） |

### 3.5 JoinRequest（加入申請，公會板路徑）

| 欄位  | 說明  |

## 4. 活動狀態機

這是整個系統最核心的邏輯之一。

### 公會層級狀態轉換

```
待練習 → 練習中 → 分析中 → 回饋期 → 待討論 → 復盤中 → 完成
                                                    （+ 已中止）
```

| 轉換  | 觸發條件 |
|-----|------|
| 待練習 → 練習中 | 第一位成員加入練習房間（通話層啟動） |
| 練習中 → 分析中 | 主持人結束錄影（不需等通話結束） |
| 分析中 → 回饋期 | AI 分析完成（系統自動） |
| 回饋期 → 待討論 | 所有成員個人進度皆「已完成」，或時間到強制推進 |
| 待討論 → 復盤中 | 第一位成員加入復盤房間 |
| 復盤中 → 完成 | 主持人結束復盤會 |
| 任何非終態 → 已中止 | 公會長手動中止 / 系統自動（待練習超時無人加入） |

**已中止為終態，不可重開。**

### 個人層級回饋進度（僅回饋期內有效）

| 進度  | 觸發條件 |
|-----|------|
| 未開始 | 初始狀態 |
| 進行中 | 使用者進入 P-22 回饋頁面 |
| 已完成 | 勾選至少 1 題復盤題目後按「完成回饋」 |

### 降級機制

回饋期截止點 = 復盤會開始時間。復盤開始瞬間，對未完成回饋的成員觸發：系統從 AI 初版分析自動挑選復盤題目（以初版修正建議作為素材）。

### 使用者看到的整合狀態

前端需要結合公會狀態 + 個人進度來顯示：

| 公會狀態 | 個人進度 | 顯示給使用者 |
|------|------|--------|
| 回饋期  | 未開始  | 待回顧    |
| 回饋期  | 進行中  | 回顧中    |
| 回饋期  | 已完成  | 待討論    |
| 其他狀態 | —    | 直接顯示公會狀態 |

## 5. WebRTC 需求規格

### 通訊形式

| 項目  | 規格  |
|-----|-----|
| 語音通話 | 必須，2-6 人多人通話 |
| 螢幕共享 | 必須，成員可分享螢幕 |
| 鏡頭視訊 | **不支援**，無鏡頭畫面 |

### 練習房間兩層結構

| 層   | 生命週期 | 說明  |
|-----|------|-----|
| 通話層 | 第一位成員進入 → 所有人離開（或最大通話時間上限） | 語音通話 + 螢幕共享，練習前後可閒聊 |
| 錄影層 | 主持人按「開始練習」→ 主持人按「結束練習」（或 90 分鐘硬上限） | 錄製全員語音 + 螢幕共享畫面，結束後送入 AI 分析 |

兩層獨立運作：錄影結束後通話繼續，成員可留下閒聊。

### 復盤房間

語音通話（無錄影、無螢幕共享需求）+ follow mode（主持人控制所有人的畫面焦點）+ 片段回放功能（回放練習錄影的特定時段）。

### 錄影規格

| 項目  | 規格  |
|-----|-----|
| 錄製內容 | 螢幕共享畫面 + 全員語音 |
| 硬上限 | 90 分鐘自動停止 |
| 後處理 | 結束後上傳 → 合成影片 → 送入 AI 分析 |
| 失敗處理 | 上傳失敗自動重試，持續失敗通知公會長，活動標記異常 |

### 主持人機制

| 項目  | 規格  |
|-----|-----|
| 指派  | 第一位進入房間者自動擔任 |
| 轉移  | 一鍵轉移給在場任何成員 |
| 離開處理 | 角色自動轉移給在場最久的成員 |
| 權限  | 啟動/停止錄影、推進流程步驟、轉移主持人 |

### 設備測試（P-20）

進入練習 / 復盤房間前的預檢頁面。測試項目：麥克風 + 連線品質。不測試鏡頭。

## 6. LLM 回饋系統

### 架構：兩個獨立但互補的系統

| 系統  | 職責  | 技術基礎 | 前期策略 |
|-----|-----|------|------|
| 初版分析系統 | 處理錄影 → 語音辨識 → 錯誤偵測 → 產出初版修正建議 + 信心度標記 | 語音處理 + 語言分析 | **人工替代**（前期） |
| AI Chatbot | 使用者對話補充意圖 → 產出/迭代修正建議 → 即時更新後端 | LLM + MCP | **直接使用 LLM**（不需人工替代） |

### 初版分析系統（前期人工替代）

Pipeline：錄影上傳 → 語音辨識（逐字稿 + 時間戳 + 說話者辨識）→ 錯誤偵測 → 每句標記信心度 → 產出初版修正建議。

前期由人工處理上述流程，產出格式需與未來 AI 版本一致（SentenceAnalysis 資料結構）。

### AI Chatbot

出現在三個場景：

| 場景  | 觸發方式 | 功能  |
|-----|------|-----|
| P-22 會後回饋 | 使用者點擊逐字稿中的句子 | 補充意圖、迭代修正建議 |
| P-23 復盤房間（第一階段） | 討論中展開側面板 | 查證文法、詞彙用法 |
| P-23 復盤房間（第二階段） | 主持人按「進入第二階段」 | 歸納跨成員錯誤 pattern、生成口說練習情境 |
| P-13 歷史記錄 | 使用者點擊逐字稿中的句子 | 繼續對話（無時間限制） |

**Chatbot 行為規則：**

* 對話歷史不保留（關閉瀏覽器後清空）
* 修正結果透過 MCP 即時寫回後端（SentenceAnalysis.correction 欄位更新）
* 使用者可對同一句子重複開啟對話迭代
* P-23 第二階段的 Chatbot 為共享畫面（所有成員看到相同內容）
* 語氣與角色設定由 Content 團隊提供，Tech 團隊轉成 system prompt

**Freemium 備忘（非 MVP）：** Chatbot 每次對話涉及 LLM API 成本。未來可考慮每次活動的免費互動額度，超過後付費。MVP 不設限。

## 7. 通知系統

### 三層管道

| 管道  | 說明  |
|-----|-----|
| 站內通知 | 基底管道，所有事件都走。鈴鐺 + 動態牆 |
| Web Push | 時效性事件。需使用者授權，授權率不可控 |
| Email | 兜底管道，關鍵事件與拉回提醒 |

三管道按事件性質獨立分配，不互斥。

### 事件清單與管道對應

**日常事件（僅站內）**

| 事件  | 通知對象 | 點擊導向 |
|-----|------|------|
| 公會長發佈公告 | 全體成員 | 動態牆  |
| 成員留言 | 相關成員 | 動態牆該則留言 |
| 新成員加入公會 | 全體成員 | 動態牆  |
| 場次內容變更（模式/主題/報告者） | 全體成員 | 動態牆  |

**時效性事件（站內 + Web Push）**

| 事件  | 通知對象 | 點擊導向 |
|-----|------|------|
| AI 分析完成（回饋期開始） | 全體成員 | 會後回饋頁 |
| 回饋期即將截止 | 未完成回饋的成員 | 會後回饋頁 |
| 練習/復盤時間快到（開始前 30 分鐘） | 全體成員 | 設備測試頁 |

**關鍵事件（站內 + Email）**

| 事件  | 通知對象 | 點擊導向 |
|-----|------|------|
| 加入申請被通過 | 申請者  | 該公會動態牆 |
| 加入申請被拒絕 | 申請者  | 公會板  |
| 新場次排定 | 全體成員 | 動態牆  |
| 場次時間變更 | 全體成員 | 動態牆  |
| 場次被中止 | 全體成員 | 動態牆  |
| 成員被移除 | 被移除者 | Dashboard |

**拉回事件（站內 + Web Push + Email）**

| 事件  | 通知對象 | 點擊導向 |
|-----|------|------|
| 復盤結束後超過 N 天未安排下一次活動 | 公會長  | 動態牆（排程 modal） |
| 註冊後幾天沒加入公會 | 該使用者 | 公會板  |
| 建立公會後幾天沒成員加入 | 公會長  | 公會設定（邀請連結） |
| 邀請連結即將到期 | 公會長  | 公會設定（邀請連結） |
| 有人申請加入公會 | 公會長  | 公會設定（加入申請審核） |

> 各「N 天」具體數值待開發階段定義。

## 8. 排程系統邏輯

### 兩種排程方式並存

| 方式  | 說明  |
|-----|-----|
| 預設時段（可選） | 公會長設定固定練習時段 + 復盤自動推算（+7 天），系統自動排出未來場次 |
| 手動排定 | 公會長隨時手動新增，與預設並存 |

### 排定活動的自動行為

排定練習時間時，系統同時建立 Activity + 兩個 Session（練習 + 復盤）。使用者感知到的是「排定一次練習」，復盤時間自動配對。

### 練習模式與設定

排定時公會長選擇：

| 設定項 | 對話練習 | 報告練習 |
|-----|------|------|
| 練習模式 | conversation | presentation |
| 公告組題目 | 公會長設定 | —    |
| 報告者指定 | —    | 公會長從成員中選 2 人（系統建議最久沒報告的） |
| 報告主題方向 | —    | 公會長設定 |

## 10. 關鍵業務規則彙整

以下為散落在各處但後端必須實作的業務規則：

| 規則  | 說明  |
|-----|-----|
| 公會加入上限 | 每人最多 3 個 |
| 公會建立上限 | 每人最多 1 個 |
| 邀請連結有效期 | 7 天，產生新連結時舊連結失效 |
| 加入申請自動取消 | 加入一個公會後，其他 pending 申請自動 cancelled |
| 練習開始條件 | 主持人啟動錄影需至少 2 人在場 |
| 錄影硬上限 | 90 分鐘自動停止 |
| 回饋完成條件 | 勾選至少 1 題復盤題目 |
| 選題上限 | 每人最多 2 題 |
| 回饋期截止點 | = 復盤會開始時間 |
| 降級機制 | 回饋期截止時未完成者，系統自動選題 |
| 主持人指派 | 第一位進房者，離開時轉移給在場最久的成員 |
| 報告練習每場 2 人 | 公會長指定，系統建議最久沒報告的成員 |
| 已完成回饋仍可修改 | 直到復盤會開始前 |
| 活動中止不可重開 | 需重新排定新活動 |
| 停滯公會 | MVP 不處理，不刪除不凍結 |

## 11. 開發階段待定義項目

以下項目在設計階段標記為「留待開發階段定義」：

| 項目  | 說明  |
|-----|-----|
| 各「N 天」拉回提醒的具體天數 | 註冊後未加入公會、建公會後無成員、復盤後未排下次 |
| 待練習自動中止的時間門檻 | 超過預定時間多久無人加入則自動中止 |
| 最大通話時間上限 | 錄影結束後通話可持續多久 |
| 降級機制自動選題邏輯 | 系統從初版分析選題的優先級規則 |
| 錄影合成的時間延遲 | 影響使用者多快能開始做回饋 |
| AI 分析的具體產出格式 | 修正建議的分類邏輯、呈現方式 |
| 公會長未審核申請的提醒天數 | 建議 3 天 |
