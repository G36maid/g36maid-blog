> 這是一篇方法論教學：如何用一個下午把整個家用網段翻過來查一遍，校準一份過時的網路圖。指令與原則都是通用的；文中的 IP 位置一律用示意值，讀者套用時換成自己的網段即可。

## 你家的網路圖，多久沒更新了

每個玩了一陣子 homelab 的人家裡，都有一張畫完就再也沒對過的網路圖：紙本筆記或某個 markdown 檔，記著「數據機在哪、AP 掛在哪個 IP、那台不知道什麼的盒子是什麼」。設備汰換、IP 漂移、WiFi 模組換代，這張圖默默過期——而你不會發現，直到某天要改設定時發現記憶和紀錄互相矛盾。

與其繼續猜，不如花一個下午把整個網段翻過來查一遍。這篇文章記錄完整方法論：**ping sweep → ARP 表 → OUI 廠商查詢 → HTTP 探測 → 授權 SSH 實證**，每一步都有可複製的指令，最後附上常見的發現與修繕方向。前提只有一個：這是你自己的網路，或你有明確授權的網路。

## 方法總覽

整個稽查的核心邏輯：

1. **先 ping 過一輪**，逼出 ARP 表——ARP 表就是這個廣播域的「在場證明」；
2. **用 MAC 的 OUI 前綴查廠商**，一個前綴通常足以辨識裝置是誰家的（Zyxel、TP-Link、Nintendo……）；
3. **對開著 web 管理面的裝置探 HTTP title**，確認身份；
4. **對自己有管理權的機器直接 SSH 進去**，用 `ip addr` / `ifconfig` 拿到不可抵賴的實證；
5. 最後**拿實測結果勘誤舊紀錄**，把不確定的項目列成清單。

一個貫穿全文的觀念：**前三步都是被動偵測，只能「推定」；只有登入裝置本身的輸出才是「實證」**。推定與實證要在筆記裡明確分開記——「同 OUI 所以大概是同一家的 repeater」是推定，哪怕再合理也不該悄悄升級成「確認」。

## 步驟一：ping sweep 與 ARP 普查

從一台與目標同 L2 的管理機先掃一輪：

```bash
# ping sweep：-sn 只做 host discovery，不打 port
nmap -sn 192.168.1.0/24
```

跑完立刻看 ARP 表——nmap 的 host discovery 會把回應過的主機灌進鄰居表：

```bash
ip neigh show
```

輸出會是一串 `IP dev lladdr [REACHABLE/STALE]` 的列表。這一步的產出就是本次稽查的骨幹：**誰在線、誰的 MAC 是什麼**。

兩個實務建議：第一，手機、筆電這類終端會隨在線狀態浮浮沉沉，普查對象應該放在「網路設備」（AP、網橋、伺服器、VM）上，終端裝置標記為快照即可。第二，`ip neigh` 之前最好自己 ping 一輪或用 nmap——ARP 表裡只有最近溝通過的鄰居，睡著的設備不會自己出現。

## 步驟二：OUI 查廠商

拿到 MAC 後，把前三個 byte（OUI）丟去查廠商。懶人做法是直接打 maclookup 的 API：

```bash
curl -s "https://api.maclookup.app/v2/macs/00:eb:d8:04:5e:5f" | jq -r '.company'
# MERCUSYS TECHNOLOGIES CO., LTD.
```

也可以到 [IEEE 的 OUI 資料庫](https://standards-oui.ieee.org/) 手動查。這一步的辨識力比想像中強，兩個好用的例子：

- `bc:24:11` 開頭是 **Proxmox VM 的預設 MAC 前綴**——看到它就知道那不是實體機，是某台 PVE 上開出來的虛擬機；
- 兩個裝置同屬 Zyxel OUI，就值得聯想它們是同一套系統的零件（例如電信商的全屋通套件）。

把普查結果整理成表。建議欄位：IP（尾碼即可）、OUI/廠商、推定身份、證據等級（推定/實證）。這張表就是接下來所有工作的座標系。

## 步驟三：HTTP 探測確認管理面

網路設備幾乎都開 web 管理頁，對 80/443 探一下 title，身份就八九不離十：

```bash
# 找出有開 web 的主機
nmap -p80,443 --open -T4 192.168.1.0/24

# 對開著的主機抓 HTTP title（自簽憑證要 -k）
nmap -p80,443 --open --script http-title 192.168.1.0/24
# 或手動：
curl -ksI https://192.168.1.1 | head -n1
```

實務上會遇到幾種情況：管理頁是 HTTPS only（自簽憑證，`curl` 要加 `-k`）；幾台 AP 各回各的管理頁面；也會有設備的工程模式被鎖住進不去（例如某些電信商客製機種近年的遠端認證鎖）。進不去的就誠實記為「無法確認」，這本身也是稽查產出的一部分——它代表你有一個待解的管理權問題，而不是假裝那台設備不存在。

## 步驟四：SSH 實證（僅限自己的機器）

對自家伺服器、路由器這種**本來就有管理權**的機器，別再推定了，直接進去拿實證：

```bash
# 確認介面狀態與位址
ssh opnsense.local ifconfig vmbr0

# 橋接介面、實體網卡狀態、鄰居表一次看
ssh pve 'ip -br addr; ip -br link; ip neigh'
```

這一步最常撈到三類關鍵事實：

1. **VM 身份確認**：某個 Proxmox MAC 的 IP 究竟是哪台 VM 的哪個介面，登入 `ip -br addr` 看一眼就有答案，不用再猜；
2. **誤判救援**：實體網卡顯示 `NO-CARRIER`，第一反應是「網卡壞了」，實際上常常只是接在上面的機器**暫時拔線**。沒有實證，這種狀態很容易被記成故障；
3. **IPv6 現況**：閘道會發 RA，內網機器可能悄悄拿了全域 IPv6——這直接影響後面的防火牆檢查（見修繕清單）。

## 步驟五：拿實測結果勘誤舊紀錄

這是整個稽查最有成就感的部分。把舊紀錄逐條對照實測，通常會收穫三類結果：

- 對的：拓撲骨架（數據機 + bridge AP + 網橋）方向正確；
- 錯的：兩台 AP 寫成同一個 IP（實測各自不同，而那個 IP 其實是**另一個地點的 AP**——這種混淆很危險，等於把信任邊界畫錯）；舊型號早已汰換但無汰換紀錄；某組 SSID 根本不存在；
- 查不到的：某些設備只能推定（同 OUI + 正常 DHCP），標清楚是推定，留待下次實證。

**教訓：網路圖不是畫完就算，要定期用實測校準；而且校準時要以「當下實測」為準，不是以「記憶」為準。**

## 稽查後常見的發現與修繕方向

翻完一個 /24，這幾條幾乎是家用網路的通病，按優先序列：

### 1. 網路設備的 IP 全在 DHCP 上漂

AP、網橋、旁路由的管理 IP 全是浮動 DHCP、無 reservation，普查表只是快照，重開機就漂。修法很直接：在閘道的 DHCP 設定裡對這些 MAC 做 reservation。如果閘道是電信商客製機種而工程帳號被鎖，正規途徑是找 ISP 處理——把「想做但被鎖在外面」的項目如實列著，比忘記它好。

### 2. 弱密碼的 AP 坐在廣播域裡

家用網路常有一個「延伸涵蓋」用的橋接設備（訊號橋、舊 AP、電力線橋），它的 WiFi 密碼往往是最弱的一環——而它直接坐在主廣播域裡。密碼被猜中，等於直接加入整個 /24，包括你的伺服器管理面。低成本收斂：**換一組強密碼，五分鐘的事**。另外要分清楚信任邊界：同家庭、同產權的延伸網段屬於同一信任網域，不是外部入侵點；真正要防的是「弱憑證讓不可信裝置進入可信域」。

### 3. 沒有訪客隔離

主要 AP 上掛了一堆無線用戶端，全部在同一個主網段，訪客網路功能沒開。訪客來了只能給主網段密碼。建議至少啟用訪客 SSID，把不受信任的裝置隔開。

### 4. IPv6 防火牆政策不可考

閘道會發 RA，終端可能拿全域 v6 直接對外。v6 防火牆政策通常在閘道上，而閘道工程模式可能進不去——這條只能掛著，等能進去了再確認。稽查的價值之一就是把這種「不知道自己不知道」的項目變成明確的清單條目。

### 5. 管理面與家用網段分流

homelab 的管理流量建議全部走 overlay（Tailscale/WireGuard 的 subnet router 廣播內部管理網段），家用網段的直連只留給消費型服務：

```text
管理機（Tailscale 100.x）
    ↓
旁路由 subnet router（廣播 homelab 管理網段）
    ↓
PVE / NAS / prod VM 的管理介面
```

這是既有防護的話，稽查時確認它仍然成立即可；還沒做的話，這是最值得補的一層。

## 踩雷與注意事項

- **bridge 模式的 AP 從外面看不出角色**：不 NAT、不發自己的網段，一定要登入管理頁確認模式，不能只看 IP 行為猜。
- **「同 OUI」不等於「同一台」**：同廠商的推定要老實標「推定」，不要在筆記裡悄悄升級成「確認」。
- **終端裝置的快照會腐爛**：手機、遊戲機、電視的 IP 與在線狀態天天變，普查表要標註快照日期，別把「上次掃到的」當成「恆常存在的」。
- **先盤點再動手**：一開始就列好待查清單（舊紀錄勘誤、未知設備身份、埠位對應……），逐項打勾，而不是邊掃邊發散——這是能否單日完成的關鍵。
- **掃自家網段就好**：這套手法對自己的 /24 是稽查，對別人的網段就是探測。nmap 的授權邊界自己顧好。

## 結語

一個下午、五個步驟，就能把一張過期的網路圖校準成「有實證的快照」，順手抓出幾個配置錯誤。這套流程沒有任何高深技術——`nmap -sn`、`ip neigh`、OUI 查詢、`curl -kI`——但組合起來的辨識力遠超乎直覺，尤其是 OUI：**一個 MAC 前綴就足以把「某個匿名 IP」變成「Nintendo 的遊戲機」**。

老實說，最難的不是技術，是「紙本紀錄過時了但沒人知道」這件事本身。建議把這次稽查的指令存成一個小腳本，每半年跑一次，diff 一下普查表——網路圖也是會腐爛的。
